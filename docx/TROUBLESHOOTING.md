## 1. 语音链路问题

### 1.1 说话完全没反应，日志里什么都没有

**现象**：节点正常启动，对着机器人说话，终端没有任何识别结果。

**原因**：平台 ASR 默认是**关闭**的（`asr open status: 0`）。业务节点必须每 0.5 秒向 `/intelligent_interaction/lyre/enable` 发布一次 `true` 来“续命”，**一旦停发，平台立刻把 ASR 关回去**。

**解决**：在节点里加定时器持续使能，退出时发 `false` 还原。

```python
# tour_chat.py
self._enable_pub = self.create_publisher(
    Bool, "/intelligent_interaction/lyre/enable", 10)
self.create_timer(0.5, self._publish_enable)   # msg.data = True
```

**验证**：

```bash
ros2 topic echo /intelligent_interaction/lyre/enable   # 应每 0.5s 有一条 true
```

**教训**：平台语音不是“订阅就能用”，而是“租用制”——不发心跳就断供。

---

### 1.2 `ros2 param get /audio_aiui ...` 报 `Node not found`

**现象**：同一条命令，第一次 `Node not found`，过一会儿又能取到参数。

**原因**：`ros2` CLI 通过 daemon 缓存节点图。节点刚启动/刚重启时缓存没刷新；或该节点当时确实没起来。

**解决**：

```bash
ros2 node list                 # 先确认节点在不在
ros2 daemon stop && ros2 daemon start   # 刷新缓存
ros2 param get /audio_aiui avvtn.wakeup_mode
```

**教训**：`Node not found` 不一定是节点没启动，先分清“节点不在”还是“缓存过期”。

---

### 1.3 `avvtn.keyword` 是空字符串，唤醒不了

**现象**：语音唤醒词怎么喊都没用。

**原因**：平台配置里 `avvtn.keyword: ""`，且 `wakeup_mode: face` —— **当前走的是人脸唤醒，不是语音唤醒**。

**解决**：

- 要人脸唤醒：站在机器人**正前方**，让它看到脸
- 要语音唤醒：改 `aiui_params.yaml` 的 `wakeup_mode` 与 `keyword`（属平台配置，需谨慎）

**注意**：`/home/nvidia/data/lyre/config/aiui_params.yaml` 是运行时副本，每次启动会被包内 YAML 覆盖（`process_param.py` 中“已存在则跳过”的逻辑被注释掉了），**改运行时副本会失效**。

---

### 1.4 `ros2 topic echo /audio_asr/iat` 一直没有输出

**现象**：`echo` 挂很久，一个字都没有。

**原因**：这不是命令用错，而是三个条件至少缺一个：

1. `audio_aiui` 节点在线
2. 有人在发使能心跳
3. 已经被唤醒（当前是人脸唤醒）

**解决**：按 1→2→3 顺序排查。

```bash
ros2 node list | grep audio
ros2 topic echo /intelligent_interaction/lyre/enable
ros2 topic echo /audio_asr/keyword      # 唤醒时会有一条
```

**教训**：话题“没数据”时，不要怀疑 echo，要怀疑**上游条件**。

---

### 1.5 只有站在正前方才听得到，侧后方完全无效

**现象**：人在机器人背后或侧面说话，既不唤醒也不识别。

**原因**：硬件与配置双重限制：

- 4 麦**线性阵列**（35 mm 间距，5 个波束），物理上就是前向拾音
- 人脸唤醒范围约 ±45°（云台 `head_angle_yaw: 45`）

**解决**：软件配置改不成 360°。可行方案：

| 方案 | 做法 | 代价 |
|---|---|---|
| 外接全向麦 | USB 麦 + 平台 `AudioMode` 切蓝牙输入 | 需平台配置 |
| 自建 ASR | 读 `/lyre/audio_stream` 自己跑 whisper | 见第 2 节 |

**教训**：麦克风阵列的拾音范围是**物理属性**，不要指望调参数解决。

## 2. 自建 ASR（faster-whisper）遇到的问题

### 2.1 一开始完全不触发识别

**原因**：只把音频丢给 whisper 不够，必须自己判断“什么时候开始说、什么时候说完”。

**解决**：能量 VAD + 预录缓冲：

- 帧能量阈值 `vad_threshold=600`
- 静音 `vad_silence_s=0.8` 秒判定一句结束
- 保留 `0.3s` 预录（pre-roll），避免吃掉第一个字
- 输入 `/lyre/audio_stream` 为 **96 kHz**，需按 `mic_rate_in` 处理

---

### 2.2 静音时模型“幻听”，输出“谢谢观看”

**原因**：whisper 在纯噪声/静音上会产生幻觉文本（训练数据里字幕的残留）。

**解决**：双重防护

1. 能量门限：低于阈值不进识别
2. 幻听黑名单：命中常见幻觉词且整句很短 → 丢弃（`_is_hotword_hallucination`）

---

### 2.3 地点名经常识别错（“乐知院”“创想谷”）

**原因**：通用中文模型对专有名词不敏感。

**解决**：

- `asr_hotwords` 注入热词（乐知院、核心力量跑酷、创想谷、跆拳道馆…）
- `asr_initial_prompt` 给上下文提示（“以下是普通话的导览对话…”）
- `asr_beam_size=5` 提高准确率

---

## 3. 大模型问题

### 3.1 模型返回的 `content` 是 `null`

**现象**：HTTP 200，但 `data["choices"][0]["message"]["content"]` 为空。

**原因**：Qwen3 系列默认开启 **thinking**，`max_tokens` 被思考内容吃光，正文没开始就截断了。

**解决**：请求体显式关闭：

```python
payload["chat_template_kwargs"] = {"enable_thinking": False}
```

**教训**：Qwen3 接 OpenAI 兼容接口时，这是**必踩的坑**，代码里已加注释防止后人删掉。

---

### 3.2 模型输出前后有废话，`json.loads` 直接崩

**现象**：模型返回“好的，结果如下：{...}”，解析抛 `JSONDecodeError`。

**解决**：先用正则抠出 `{...}` 再解析，并做类型校验。

```python
def _extract_json(text):
    match = re.search(r"\{.*\}", text or "", re.S)
    if not match:
        return None
    try:
        return json.loads(match.group(0))
    except json.JSONDecodeError:
        return None
```

**教训**：永远不要对模型输出直接 `json.loads`。

---

### 3.3 模型“编造”了一个地图上没有的地点

**现象**：模型返回 `{"selected": "咖啡厅"}`，导航直接失败。

**解决**：**白名单校验**——模型给的名字必须能被 `PlaceBook.resolve()` 在地图上找到，否则整条结果丢弃。

```python
place = self._places.resolve(selected)
if place is None:
    return None
```

**教训**：模型只负责“猜”，代码负责“验”。**模型永远不直接指挥底盘。**

---

### 3.4 搞不清大模型到底在本地还是远程

**排查过程**（可复用）：

1. 代码里搜地址：全部是 `http://120.48.75.178:7006/v1`，**公网 IP**
2. 搜 `dashscope|aliyuncs|openai.com`：**无命中** → 不是官方 API
3. `api_key = "EMPTY"` → 官方必 401，说明服务端不校验
4. 模型名 `122B-A10B` 是开源权重命名，官方 API 用 `qwen-plus` 这类产品名
5. 全盘搜 `*.gguf` / `*.safetensors`：**没有模型权重**
6. `/etc/systemd/system` 搜 `vllm|llama`：**无服务**
7. `/home/nvidia/logs` 搜 vllm：**无日志**

**结论**：远程自建 vLLM，机器人只当 HTTP 客户端。

**教训**：判断“本地/远程”不看注释（注释写的是“本地千问”），看**地址、权重、进程、日志**四件套。

---

### 3.5 网络一断，整台机器人变哑巴

**原因**：`QwenClient` 是单端点直连，失败直接抛异常，**无重试、无兜底、无冷却**。

**现状处理**：`chat()` 失败时播报固定话术“我这边暂时联系不上大模型”。

**建议（未实施）**：

- 一次短重试（间隔 0.5s）
- 备用端点（官方 API 或本地小模型）
- 超时从 30s 降到 8~10s

---

### 3.6 远程服务裸奔（安全问题）

**现象**：`http://` 明文 + `api_key=EMPTY`。

**风险**：任何知道 `120.48.75.178:7006` 的人都能直接调用，消耗算力；对话内容在公网明文传输。

**建议**：vLLM 加 `--api-key`，前置 Nginx + HTTPS，代码填入真实 key。

## 4. 对话体验问题

### 4.1 自问自答：机器人把自己的播报当成用户指令

**原因**：喇叭声音被自己的麦克风收回，ASR 再转成文字。

**解决**：回声判定——文本 ≥8 字且与上一句播报相似度 ≥0.5 就丢弃（`_echo_of`）；另外播完后留 2 秒静默期（`_speech_until`）。

---

### 4.2 同一句话被处理两次

**原因**：平台 ASR 会重复输出最终结果。

**解决**：2 秒去重窗口，比对去空白后的文本。

---

### 4.3 上一句还没播完就开始听下一句

**原因**：TTS `append` 是异步的，调用返回不代表播完。

**解决**：`append` 后每 0.2 秒 `query` 状态，见到 `playing` 后再连续 0.4 秒非 `playing` 才算播完。

---

### 4.4 长句播报把线程卡死

**解决**：给等待设上限 `min(预计时长×2+5, 40)` 秒；预计时长按字数估算（`len(text)*0.22`）。

---

### 4.5 一调大模型整个节点就卡住

**原因**：ROS 回调跑在单线程 executor 里，模型请求阻塞 1~3 秒 → 订阅、定时器、TTS 全部停摆。

**解决**：回调只入队，`_handle` 放到独立工作线程串行执行。

```
回调 → queue.put() → 工作线程 → 大模型/导航/播报
```

**副作用（有意）**：串行保证对话历史不被并发写乱。

---

### 4.6 上一个访客聊的内容影响下一个访客（遗留）

**现象**：`_turns` 从不清空，历史持续累积。

**建议**：回到待命点时调用 `self._qwen.reset()`（当前代码**未实现**）。

## 5. 导航问题

### 5.1 报“定位未就绪”，车不动

**原因**：切地图后 SLAM 需要重新收敛，期间位姿不可信。

**解决**：`ensure_map()` 里等待定位（最多 60 秒），并自动触发重定位（最多 3 次）；仍失败则明确提示“请把车放到已知点位”。

**关键原则**：**定位没好绝不允许移动**。

---

### 5.2 底盘报导航失败，但车其实已经到目的地了

**原因**：最后 1 米反复调整姿态，底盘超时上报失败。

**解决**：距离兜底——当前位姿距目标 ≤ `1.0 米` 时按“已到达”处理。

---

### 5.3 前方有人挡住，车停了但不说话

**原因**：底盘因障碍停车只上报故障码，不会主动播报。

**解决**：识别 DTC `0x08020005` → 播报“请让一让”，并加 15 秒冷却防刷屏。

---

### 5.4 导航途中说话，车乱改目标

**原因**：导航期间收到新指令会触发第二次任务，与当前任务冲突。

**解决**：`_navigating` 标志位，导航期间 `_enqueue` 直接忽略新输入；开始导航时清空队列。

---

### 5.5 不同地图的点位名不一致

**解决**：`places.yaml` 的别名允许配多个候选目标，运行时取“当前地图上存在的那个”。

```yaml
aliases:
  乐知教育: [乐知教育, 乐知院]
```

解析时用 `next(存在即取, None)`。

---

### 5.6 想“逐点巡线讲解”，但机器人只直达目标（遗留）

**原因**：`places.yaml` 里配了 `main_line` / `branches`，`PlaceBook` 也解析了，但 `tour_chat._navigate` **没有使用**，只有一句 `self._nav.goto(place.poi)`。

**影响**：无法实现“从乐知教育依次经过核心力量跑酷、创想谷…”。

**建议**：把主线顺序接进 `_navigate`（需改代码，未实施）。

## 6. 工程与环境问题

### 6.1 项目结构混乱，包在磁盘上缺失

**现象**：原骨架有 6 个包，但磁盘上只存在部分目录，git 索引里还有记录。

**处理**：以 `git status` / `git ls-files` 为准，确认哪些是真实存在的源码，避免误判“文件丢了”。

---

### 6.2 想把大模型搬到本地，磁盘够不够

**结论**（按 Q4 量化估算）：

| 模型 | 权重体积 | 备注 |
|---|---|---|
| Qwen3-30B-A3B | ~19 GB | 推荐，激活仅 3B，速度快 |
| Qwen3-Next-80B-A3B | ~45 GB | 质量更高 |
| Qwen3.5-122B-A10B | ~67 GB | 128GB 内存可装，速度 12~20 tok/s |
| 原始 BF16 权重 | ~245 GB | 不建议 |

**注意**：vLLM 吃原始 safetensors，llama.cpp 吃 GGUF，**后者磁盘占用约为前者的 1/3**。

---

### 6.3 Jetson Thor 上编译 llama.cpp 跑成了 CPU 速度

**原因**：未指定 CUDA 架构，Thor 是 **11.0**。

**解决**：

```bash
cmake -B build -DGGML_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=110
```

## 7. 通用排查方法论（这次总结出来的）

| 步骤 | 做法 |
|---|---|
| 1. 分层定位 | 语音层 / 业务层 / 模型层 / 导航层，先确定问题在哪一层 |
| 2. 看上游 | 话题没数据，先查上游节点和前置条件（使能、唤醒、定位） |
| 3. 用替代输入 | 语音不通就用 `ros2 topic pub /tour/chat` 验证业务逻辑 |
| 4. 单一变量 | 一次只改一个参数，避免“改了五个地方不知道哪个生效” |
| 5. 留证据 | 每句话落盘日志（`~/guide_logs/`），终端滚走也能回溯 |
| 6. 查四件套 | 判断服务在不在：地址、权重、进程、日志 |
| 7. 分清物理与软件 | 拾音范围、算力这类是物理限制，别在软件里死磕 |
